## 1. 整体架构

```
用户浏览器
    │
    ▼
接入层（单轨：Compose + Caddy）
  └─ Caddy 反向代理（HTTPS 自动签发/续期，`COMPOSE_PROFILES=https` 门控）
    │
    ▼
Express 后端 (Port 3000)  ── 生产下同一个进程直接托管 app/dist 静态文件（server.js 的 `if (fs.existsSync(distPath))` 分支）
    │                        开发下前端跑 Vite dev server (Port 3001)，由它代理 /api → 3000
    │  SQL                      │  HTTP(可选)
    ▼                           ▼
SQLite 数据库                Meilisearch (7700)
(同物异名.db / 学科词库.db    **未启用**：探测失败自动
 / 语义词典.db；知识图谱       回退 SQLite LIKE
  nodes·links 也直接读 SQLite)
```

请求链路：`中间件层(安全/限流) → 路由层(分发) → 服务层(业务逻辑) → 数据库层(SQL 操作)`

### 2.2 API 客户端架构

前端采用两层 API 抽象：

- **client.ts**：底层 HTTP 封装，自动重试 3 次、30 秒超时、统一错误处理、自动解包 `{ success, data }` 响应
- **services.ts**：上层业务函数，每个后端接口对应一个具名函数，组件只调用这些函数

调用链路：`组件 → services.ts 函数 → client.ts apiClient → fetch → 后端API`

### 3.2 中间件层

| 中间件 | 功能 | 限制 |
|--------|------|------|
| `rateLimiter` | 通用限流 | 1000 请求/分钟 |
| `searchRateLimiter` | 搜索限流（挂在 `/api/v1/terms/search`） | 600 请求/分钟 |
| `adminRateLimiter` | 管理接口限流 | 300 请求/分钟 |
| `createRateLimiter(10, 60*1000, "ai")` | AI 接口限流（`server.js` 内现建） | 10 请求/分钟 |
| `securityHeaders` | 安全响应头 | X-Content-Type-Options, X-Frame-Options 等 |
| `bodySizeLimit` | 请求体大小限制 | 1MB（超出返回 413 `PAYLOAD_TOO_LARGE`） |
| `adminAuth` | 管理员 Token 认证 | x-admin-token 请求头；无效 401 `UNAUTHORIZED`，未配置 500 `ADMIN_NOT_CONFIGURED` |
| `sqlInjectionCheck` | SQL 注入检测 | 命中返回 400 `INVALID_INPUT` |

> 限流器基于内存 Map（超限先 429 `RATE_LIMITED`，随后进入黑名单并返回 403 `BLOCKED`：通用 `rateLimiter` 封禁 1 分钟，`createRateLimiter` 工厂生成的 search/admin/ai 限流封禁 10 分钟），仅单进程有效。部署方式是单容器（`twym` 服务，只有一个 Node 进程），所以限流正常工作；若将来横向扩容需改用共享存储（如 Redis）。

### 3.4 缓存设计

缓存服务 (services/缓存.js) 核心 API：

- `cache.get(key)` / `cache.set(key, value, ttlMs)` — 读写缓存
- `cache.invalidate(...keys)` — 清除指定缓存
- `cache.invalidatePrefix(prefix)` — 按前缀批量清理
- `cache.remember(key, fetcher)` — 缓存或回源

默认 TTL：`cache.set` 按 `_DEFAULTS[key]` 精确匹配，未命中则兜底 **5 分钟**；现有调用方（词条/图谱/对比/情景/统计）全部使用默认，即实际均为 5 分钟（`_DEFAULTS` 中的 `stats` 键匹配不到实际 key `stats_summary`）。缓存最大 500 条，超出时淘汰最早写入的 20%。

### 3.5 搜索降级机制

**当前 Meilisearch 未启用**：`backend/bin/meilisearch.exe` 已删除，无任何外部搜索服务，也无需启动步骤。

`services/Meilisearch服务.js` 读取 `MEILI_HOST`（默认 `http://localhost:7700`）与 `MEILI_KEY`；未设置 `MEILI_KEY` 时 `getClient()` 直接返回 null，`isAvailable()` 探测失败即由 `services/词条.js` 回退到 SQLite `LIKE` 查询。因此 `/api/v1/terms/search` 默认走 SQLite LIKE，无需任何外部服务。写路径（新增/更新/删除词条）仍会调用 `meili.addDocument/updateDocument/deleteDocument`，但均以 `.catch(() => {})` 静默忽略失败，未启用状态下不影响业务。

### 4.2 SQLite 基本信息

- 主库路径：`data/同物异名.db`（可通过环境变量 `DB_PATH` 覆盖）
- `学科词库.db` / `语义词典.db` 由 `routes/学科词库.js`、`routes/语义.js` 各自用独立只读连接打开，不走 `db/入口.js`
- 驱动：better-sqlite3（同步 API，直接读写磁盘文件）
- WAL 模式：已启用，支持读写并发
- 外键约束：已启用
- 中文表名列名，启动时自动检测并添加缺失列

| 子领域名称 | TEXT | 主键，取值即学科词库分表名 |
| 核心学科 | TEXT | 关联 `学科.学科名称` |
| 词条数量 | INTEGER | 统计用 |
| 显示顺序 | INTEGER | 排序序号 |
| 描述 | TEXT | 说明 |
| 创建时间 / 更新时间 | DATETIME | 时间戳 |

**词条纠错建议表 (词条纠错建议)** — `/api/v1/community/suggestions*` 的数据源

字段：`建议ID`(自增主键)、`词条ID`、`词条名称`、`纠错类型`、`建议内容`、`提交者标识`、`状态`(默认"待审核")、`审核备注`、`审核时间`、`创建时间`
（`词条纠错建议`、`学科子领域映射` 均由 `db/入口.js` 启动期 `CREATE TABLE IF NOT EXISTS` 自动建表；学科子领域映射的初始 19 行随主库文件带过来）

**概念抗体表 (概念抗体)**：`抗体ID`(主键)、`词条ID`(外键 → 词条)、`抗体标题`、`抗体描述`、`抗体类别`、`抗体内容`、`创建时间`、`是否启用`。

- 建表在 `schema.sql`，但 **`是否启用` 不在 `schema.sql` 里**：由 `db/入口.js` 启动期用 `prepare("PRAGMA table_info(概念抗体)")` 判列后再 `ALTER TABLE ... ADD COLUMN 是否启用 INTEGER DEFAULT 1`。这样老库能平滑升级，且新列不改变已有行的可见性。
- 读取口径统一为 `COALESCE(是否启用, 1) <> 0`——经 `ALTER` 补出来的 NULL 行按**上架**处理，行为与该列存在之前一致。
- 写入按 `抗体ID` upsert，用的是 `ON CONFLICT DO UPDATE` 而不是 `INSERT OR REPLACE`：`REPLACE` 会删行重插、把 `是否启用` 打回默认值，等于「已下架条目被编辑一次就偷偷重新上架」。
- 补列判据必须用 `prepare + PRAGMA table_info`。用 `exec("SELECT sql FROM sqlite_master ...")` 判存在再 ALTER 的写法一次都不会生效（`db.exec()` 返回的是连接对象本身，拿不到行），代码里留着这条教训的注释。

**概念对比表 (概念对比)**：存储两个概念的对比信息，包含各自的通俗解释、表现、类比、解决方法。

**情景还原表 (情景还原 + 情景对话)**：存储真实场景和对话，揭示术语包装的真相。

**高薪技术岗表**：`岗位分类 → 岗位 → 岗位学习阶段 → 岗位技能 / 岗位学习资源 / 岗位项目 / 岗位知识卡片`

### 4.5 SQLite 表关系

`schema.sql` 中真实声明的外键（均 `ON DELETE CASCADE`）：

```
词条 ←─ 学习路径.词条ID
     ←─ 概念抗体.词条ID
岗位分类 ─1:N→ 岗位 ─1:N→ 岗位学习阶段 ─1:N→ 岗位技能
                        ├─1:N→ 岗位学习资源 / 岗位项目 / 岗位知识卡片
职业解构 ─1:N→ 职业阶段 / 职业技能 / 职业资源 / 职业项目
产业拆解 ─1:N→ 产业链环节 ─1:N→ 产业岗位
情景还原 ─1:N→ 情景对话
```

仅逻辑关联、**未声明外键**：`学科 → 词条`（靠 `学科名称`/`学科` 文本匹配）、`图谱关系.源节点ID/目标节点ID → 词条`、`概念对比` 与 `情景还原` 之间无从属关系、`学科子领域映射.核心学科 → 学科`、`词条纠错建议.词条ID → 词条`。

## 5. 关键模块说明

### 5.1 数据库层 (db/入口.js)

导出接口：`initDB`, `prepare`(预编译 SQL), `exec`(执行 SQL), `reloadDB`(重新加载), `markDirty`(标记写入并清缓存), `closeDb`。

设计原则：直接读写原始数据库文件，写入操作立即同步到磁盘，无定时保存机制，避免覆盖外部修改。

- `prepare(sql).run(...)` 返回的 `{changes, lastInsertRowid}` 必须取自**语句的执行结果**。better-sqlite3 的 Database 对象上没有这两个属性（容器内实测 `"changes" in db === false`），从 `数据库实例` 上取会恒得 `undefined`，而全仓 30 多处调用方都在读它们：提交接口回 `data:{}`（没有 `建议ID`）、`if (结果.changes === 0) throw "NOT_FOUND"` 永不触发（改了不存在的行也报成功）、`deleted += info.changes` 变成 `NaN`。

### 5.2 缓存 Key 规范 (utils/缓存键.js)

命名规则：`模块_功能_参数`，由 `buildCacheKey(base, ...params)` / `buildPageKey(base, page, pageSize, filter)` 拼接（空参数转成 `null`，列表分页无学科过滤时为 `all`）。示例：`terms_list_1_50_数学`（学科 `数学` 的词条列表第 1 页）、`terms_hot`（热门词条）、`graph_nodes`（图谱节点）。
